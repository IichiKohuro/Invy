# 0008. Архитектура клиента: Client.Core, сеанс, живые обновления, UI

**Статус:** Принято (фаза 2, 2026-11-04)

## Контекст

Desktop (Windows) и Android показывают одни и те же данные и формы. Логика должна тестироваться без UI и без Windows, работать с триммингом на Android и переживать обрывы связи в домашней сети. Типы вещей пользователь создаёт сам, поэтому формы строятся динамически.

## Решение

1. **`Invy.Client.Core` — без Avalonia.** API-клиент, подключение, SignalR, справочники, ViewModels (CommunityToolkit.Mvvm). UI-слой (`Invy.Client.UI`) — только View, конвертеры и реализации платформенных сервисов.
2. **Свой API-клиент вместо Refit.** `InvyApiClient` поверх `HttpClient` и source-generated `InvyJsonContext`: без рефлексии и генерации прокси (тримминг Android), ошибки сервера — `ApiException` с ошибками по полям (422) и актуальной версией записи (409). План предполагал Refit; заменено.
3. **Сеанс — `ClientSession`.** Подключение, справочники (`CatalogStore`), живые обновления (`RealtimeService`), кэш фото (`PhotoCache`: память + диск, по id — файлы неизменны), диалоги (`IDialogService`), диспетчер UI. Страницы создаются под сеанс; «Сменить сервер» закрывает сеанс и пересоздаёт страницы.
4. **Подключение одним действием** (`ConnectViewModel` → `ServerConnection`): сохранённый токен → «Доверенная сеть» → сопряжение с 6-значным кодом; администратор одобряет запрос из всплывающего вопроса (`PairingPrompt`). Токен на Windows шифруется DPAPI.
5. **Живые обновления.** `RealtimeService` помнит последний `seq`, догружает пропуски через `/sync/changes`, переподключается бесконечно. Если канал не поднялся при старте, сеанс работает без него и пробует снова каждые 15 с. Страницы реагируют на `ClientSession.Changed` — справочники к этому моменту уже обновлены.
6. **«Проводник»** (`ExplorerViewModel`) перечитывает только затронутое: текущее место, видимые вещи, ветки дерева (слияние узлов по id — раскрытые ветки не схлопываются). Устаревшие ответы отбрасываются по номеру запроса; обновление, пришедшее во время перехода, не отменяет переход.
7. **Формы.** Редактор вещи — отдельное окно (в FluentAvalonia одновременно открыт только один `ContentDialog`, а из редактора открываются выбор места и вопрос о конфликте). Поля — `FieldTemplateSelector` по типу данных. Ошибки сервера показываются у своих полей; конфликт версий — вопрос «Сохранить мои / Загрузить новую». Конструктор типа показывает живой предпросмотр — тот же `ItemEditorViewModel` в режиме предпросмотра.
8. **Тесты.** ViewModel — против настоящего сервера в памяти (`WebApplicationFactory`, SignalR через Long Polling); View — headless Avalonia со снимками на живых данных; сквозная проверка настоящего приложения — [отчёт фазы 2](../checks/phase-2/README.md).

## Проверка

- 60+ тестов клиента: редактор (авто-название, «запоминать последнее», 422 у полей, 409), «Проводник» (дерево, вырезать/вставить, перемещение, удаление с выбором для содержимого, обновление от второго клиента), фото (отложенная загрузка для новой вещи, обложка, кэш на диске без сервера), конструктор типов, справочники, теги, сопряжение с одобрением.
- Сквозная проверка: задержка до второго устройства — медиана 19 мс, максимум 60 мс.

## Последствия

- `IDialogService` для Android (фаза 6) — своя реализация: страницы вместо окон.
- Своя иконка из картинки — пока только фото самой вещи (`IconKind.Custom` = id фото); отдельной загрузки иконок для типов нет.
- Кэш фото на диске не чистится (фото неизменны, объём — превью 256 px); очистка по размеру — при необходимости.
- Шаблон авто-названия реализован дважды (сервер и предпросмотр на клиенте) — правила держатся одинаковыми тестами.
