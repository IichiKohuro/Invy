# 0001. SQLite FTS5 и кириллица

**Статус:** Принято (спайк фазы 0, 2026-11-04)

## Контекст

Поиск — ключевая функция Invy, данные в основном на русском. Нужно убедиться, что SQLite из `Microsoft.Data.Sqlite` (бандл `e_sqlite3`) справляется с кириллицей: регистр, «ё», префиксы, ранжирование, сортировка — и укладывается в цель p95 ≤ 100 мс на 50 тыс. вещей.

## Что показал спайк

| Проверка | Результат |
|----------|-----------|
| Версия SQLite в бандле | 3.53.3, FTS5 включён, `VACUUM INTO` и JSON доступны |
| Встроенные `lower()`, `LIKE`, `COLLATE NOCASE` | **Не работают с кириллицей** (`lower('КАБЕЛЬ')` = `КАБЕЛЬ`) |
| FTS5 `unicode61`: регистр кириллицы | Складывает (`КАБЕЛЬ` находит «Кабель») |
| FTS5 `remove_diacritics 2`: «ё» → «е» | **Не складывает** — работает только для латиницы (`cafe` находит «Café») |
| Префиксный поиск `"кабел"*` | Находит «кабели», «кабель», «кабельный» |
| Слово через дефис `usb-c` | Токенизатор делит на `usb` + `c`; запрос строится как фраза `"usb" + "c"*` |
| `bm25` с весами колонок | Совпадение в названии выше, чем в описании и месте |
| `highlight()` | Возвращает исходный текст с отметками совпадений |
| Скорость, 50 тыс. записей, топ-50 по `bm25` | p95: 6–28 мс для типичных запросов; худший случай (одна буква, совпадают все записи) — 60 мс |

Проверки закреплены тестами: `tests/Invy.Infrastructure.Tests/Sqlite/CyrillicSearchTests.cs`, `FtsQueryTests.cs`, `tests/Invy.Domain.Tests/Text/*`.

## Решение

1. **Нормализация в .NET** — `Invy.Domain.Text.TextNormalizer`:
   - `Normalize` — для колонок `*Norm`, сравнений и запросов: NFKC → нижний регистр → «ё» в «е» → схлопывание пробелов;
   - `ForFullTextIndex` — для индекса FTS5: NFKC и «ё/Ё» в «е/Е», **регистр сохраняется** (его складывает `unicode61`), поэтому `highlight()` показывает почти исходный текст.
2. **Запрос FTS5 строится только через `FtsQuery`**: каждое слово нормализуется и берётся в кавычки, последнее — префикс; пользовательские `AND`, `NEAR`, `*`, `"` остаются обычным текстом. Полноценный язык запросов — фаза 3.
3. **Сортировка** — коллация `RU_NATURAL` (`NaturalStringComparer`): без учёта регистра и «ё», числа по значению («Коробка 2» < «Коробка 10»).
4. **Каждое соединение** настраивается через `SqliteConnectionSetup.Configure`: коллация, функция `invy_norm()`, PRAGMA (`WAL`, `foreign_keys`, `busy_timeout = 5000`, `synchronous = NORMAL`). Для EF Core — через `DbConnectionInterceptor` (фаза 1).
5. Схема FTS5 — как в PLAN.md (6 колонок, `unicode61 remove_diacritics 2`, `prefix = '2 3 4'`), `rowid` = `Items.Number`.

## Последствия

- Функцию `invy_norm()` и коллацию `RU_NATURAL` знает только наше соединение: в индексах по выражениям и в `CHECK` их не используем, иначе БД не откроется сторонними инструментами (DB Browser и т. п.). Вместо этого храним готовые колонки `NameNorm`.
- Морфологии нет: «кабелями» по запросу «кабель» находится только за счёт префикса. Стемминг (Snowball) — в бэклоге.
- Dapper использует Reflection.Emit: на сервере это нормально, но в клиентах (Android, тримминг/AOT) Dapper не применяем.
